# 日常同步狀態的持久化與重啟恢復設計

日期：2026-09-05

狀態：方案方向已確認；本書面規格待使用者審閱，尚未實作。

版本：1.7.0（13）。核對基準：`95f244288ee98654d8e5d87002ec8befd30aa871`。

## 目標與範圍

補齊第四階段正式 App 接線前的必要條件：首次移轉後，每次日常提交都保存精確同步狀態，程序中斷再開啟時仍能繼續編輯與同步，不從本機畫面資料或時間戳猜回版本。

本規格只涵蓋 Core 持久化、既有發布交易整合、移轉銜接、重啟恢復及隔離測試。不啟用正式 CloudKit、Keychain 或 App 宿主，不修改 UI、購買、語系、版本、簽名或發布設定。第四階段原計畫的正式接線與實機驗收仍是後續工作。

## 已確認方案與現況

沿用 `JSONProjectStore.commitArchiveAndPublish`、`publish` 與既有 publication transaction 的提交／恢復權威；不另建獨立的日常交易協調器或資料庫。

目前 `hydrateSyncBootstrap` 只把已驗證移轉 checkpoint 載入記憶體，並明確要求後續發布推進持久化 canonical 狀態。`publish` 保存版本收據、附件依據、同步日誌與刪除帳本後移除交易標記，但尚未保存完整日常 canonical checkpoint。僅有 archive 或未送出的日誌，不能重建已 ACK 的欄位版本、墓碑與附件歷史。

不採用第二套獨立寫入流程：它需要額外處理 archive、同步狀態與兩套交易之間的提交順序，增加不一致情況。也不採用重啟時重新分配版本，因為這會改變既有合併及重播結果。

## 元件與資料權威

- 新增獨立 Core checkpoint 儲存元件，負責有界讀取、格式／摘要驗證與耐久替換；交易決策仍由既有 publication transaction 負責。
- 帳號 working set 下使用 `SyncMetadata/canonical.json`。既有 `bootstrap-canonical.json` 仍是首次移轉證據，不在每次編輯時改寫。
- 日常 checkpoint 保存格式版本、帳號範圍識別、提交識別、archive 摘要與完整已驗證 canonical records，包括墓碑、欄位版本、原始 mutation／attachment 識別、前驅及計數器／Watch 原子狀態。
- 附件內容仍由既有附件檔案與不可變來源依據持有；checkpoint 不複製大型媒體，也不改寫已發出的來源 URL。必要依據必須在重開時交叉驗證，不能用新識別替代缺失依據。
- 待送日誌不等於完整 checkpoint；ACK 與日誌壓縮不得移除仍需保存的 canonical 狀態。永久刪除依據沿用既有 ledger，不因 checkpoint 更新而重置。
- 編碼後 checkpoint 及其交易承載資料分別必須有明確的 100,000,000 bytes 上限，超限在修改正式資料前拒絕；不默默截斷 records 或歷史。

## 提交流程

1. 在既有帳號獨占與發布凍結範圍內讀取已驗證的前一 checkpoint；使用已分配的精確版本與這次候選資料計算下一狀態。
2. 既有交易標記在改寫 archive／附件前，耐久保存足以恢復下一 checkpoint 的完整依據，綁定前後狀態摘要與同一提交識別。採用同一標記承載有界候選狀態，不新增另一套提交意圖檔。
3. 沿用既有 archive／artifact commit 判斷，不以記憶體 callback 是否執行判斷磁碟提交。
4. 提交已成立後，精確重播版本收據、附件依據及 journal；耐久安裝對應 checkpoint，完成既有附件 manifest／刪除或復原帳本確認，最後才移除 publication transaction。
5. 檔案與父目錄同步成功才算耐久完成。rename 後同步失敗仍保留交易權威，重試重新驗證並完成同步；不能只因檔案可讀就回報完成。

新流程須涵蓋 archive 編輯、附件專用提交、Watch metadata、刪除與復原等所有既有中央提交路徑。相同 archive 摘要不表示同步狀態相同：必須用提交識別及精確 records 區分只改同步狀態的提交。真正無變更操作不分配新版本。

現有已提交資料後的錯誤語意保留：不得回滾已證明提交的使用者資料；保留交易並阻擋後續 mutation／同步發布，直到恢復完成。一般離線或雲端不可用不是本機損壞，不因此阻擋編輯。

## 首次銜接與重啟

- 首次從移轉 checkpoint 建立日常 checkpoint，只能在移轉終態與 archive／附件依據驗證通過、凍結仍持有時進行。精確沿用 records，不重新配置版本。
- 未有日常 checkpoint 但有有效首次移轉證據時，可完成上述單次銜接；不存在或不相符的必要證據不得被當作空白帳號。
- 已存在日常 checkpoint 時，以它及未完成交易判定當前狀態；不能退回使用較舊移轉 checkpoint 掩蓋損壞或不一致。
- 啟動必須先恢復 publication transaction，再對照 archive、checkpoint、附件與既有 ledger，最後才允許提供可編輯 store／發送同步。Core 提供明確恢復入口，正式 App 呼叫接線留在後續階段。
- 未提交交易保留前態並按原有安全規則清理；已提交交易完成同一後態與同一日誌批次；不明、錯帳號、損壞或無法證明的混合狀態拒絕且保留證據。
- 舊版 transaction 只依已有恢復依據處理；如果不能證明完整 canonical 狀態，保持需要修復，不偽造轉換。未啟用同步的既有本機 store 維持原行為。

## 帳號與安全邊界

沿用 `SyncAccountStorage` 的帳號隔離與獨占；MainActor 不是跨程序鎖。checkpoint 與交易內容必須綁定目前帳號，不允許跨帳號重播。

遵守既有 no-follow、安全普通檔案讀取、摘要檢查與有界配置規則。新檔案必須納入既有帳號 inventory／清理驗證；不得因此把全部已 ACK 歷史擴張成待同步加密備份。若原帳號恢復只能提供待同步子集，必須等待後續雲端重取補齊，不能把子集冒充完整 checkpoint。

不掃描或修補真實使用者資料，不以刪檔解除無法證明的狀態。測試僅使用獨立暫存帳號目錄與注入依賴。

## 驗收條件

- 真實 Core store／journal：移轉 → 編輯 → 銷毀實例 → 重開 → 再次編輯，前次精確版本保持，新版本單調且無重複發布。
- 日誌 ACK 並壓縮後重開，仍保有已確認 canonical records、墓碑與附件版本依據。
- 在交易標記、archive／artifact 提交、journal、checkpoint 替換、父目錄同步及交易移除各邊界注入失敗；重開結果為可證明前態或同一後態，否則明確拒絕。
- checkpoint 寫入成功但交易清理失敗的重試不產生第二組版本或第二次 domain 效果；相同 archive、不同同步狀態能正確恢復。
- 六個計數器與 Watch 原子證據、metadata-only 更新、兩類標註、刪除／第 29 天復原均跨重開保留，未同步模式行為不變。
- 錯帳號、損壞摘要、缺失必要附件依據、超額、舊交易缺少完整依據均拒絕且不改寫原始證據。
- 帳號 inventory／封存清理及 pending-only 復原回歸，避免新增 checkpoint 打破第三階段協定。

先逐項測試 RED／GREEN，再執行相關 Core 回歸及停用簽名、不啟動宿主的專案 build-for-testing。完整平台與真實程序終止驗收另記證據；單純建立新物件不宣稱已驗證斷電耐久性。

## 完成界線

本子階段完成是上述持久化與恢復契約有實作、測試及審查證據，不代表完整同步上線。正式 domain／UI、遠端批次合併提交、墓碑媒體重取、永久標記傳輸、完整測試與 iPhone／iPad／Mac／Watch 驗收仍由第四階段後續處理。推送、部署、上傳與送審不在本次授權範圍。
