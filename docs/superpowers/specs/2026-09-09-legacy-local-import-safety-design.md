# 舊本機資料明示匯入：安全與交易邊界

日期：2026-09-09。版本維持 1.7.0 (13)。原始碼基準：`1ca60ef2322e0bd024695b223d2654f23becff34`，分支 `docs/cross-device-sync-design`。

狀態：使用者已分別同意來源處理方向與匯入安全機制；本書面規格待整份審閱。未開始實作，不代表同步啟用、實機驗收、推送或送審批准。

## 1. 範圍與已確認決定

本規格只定義舊本機資料的明示匯入安全契約與驗收界線，不一次設計 Watch 新協定、zone provisioning、正式 App factory 或整個發布流程。

使用者已確認：

- 無法確認歸屬的舊本機資料保留本機，不自動併入目前 iCloud 帳號；另設明示確認匯入流程。
- 先完整備份、隔離準備及合併驗證，成功前不取代原資料。
- 確認只適用當次帳號與來源版本；切換帳號或新增編輯後重新確認。
- 取消、失敗或突然關閉時保留原資料與復原證據。
- 舊 Watch 待送指令不因匯入而改綁至新帳號。

採用明示匯入而不採固定路徑自動接入：多一次使用者確認，但不把缺乏歷史證據的 archive 當成從未綁定。也不以全面延期所有來源的同步取代這個精確界線。

上位契約為 `2026-09-02-cross-device-icloud-sync-design.md` 與 `2026-09-06-cloud-sync-app-session-lifecycle-design.md`。本次只補充合法可用的 legacy 本機內容如何取得明示匯入意圖；不放寬已綁帳號資料的身分驗證、隱藏、復原及跨帳號禁止規則。

## 2. 來源分類與權限

「歷史歸屬不明」與「目前無權讀取」是兩回事。使用者按確認不能解鎖無權讀取的資料。

| 來源 | 本規格允許的行為 |
| --- | --- |
| 合法既有本機會話內可讀資料，但沒有從未綁定的正面證據 | 不自動同步；可以準備本規格的明示匯入 |
| 有原生正面證據的從未綁定來源 | 仍由其既定來源契約處理；本切片不新增自動資格 issuer |
| 已綁目前帳號的 working set 或 recovery | 走原帳號正常復原／重開，不重新包裝成 legacy 匯入 |
| 已綁其他帳號、目前身分未知的帳號資料、無法驗證的 recovery | 保留並遵守原有遮蔽／拒絕規則；確認按鈕不能繞過 |
| 損毀、缺附件、未知格式或來源驗證失敗 | 不匯入、不補空檔；保留原始資料並顯示可處理原因 |

固定路徑、installation UUID、沒有 marker、caller Boolean 或使用者確認都不是「歷史從未綁定」證據。來源安全分類失敗時不得降級成第一列。

明示確認是把已合法取得的這一份內容匯入指定目的帳號的意圖，不是移交舊帳號的 journal、engine state、key、epoch、recovery authority 或 Watch 指令。即使包裝成備份，其他帳號的受保護 working set 仍不得由此入口讀取或搬移。

## 3. 元件責任與契約

以下為責任名稱，不聲稱已存在對應 API。

- **來源擷取器**：在合法來源會話下讀取完整內容與參照附件，建立可重驗的來源版本及受驗證備份；不簽發帳號或安裝權限。
- **確認協調器**：由 App 的單一 owner 管理，一次只接受一個當前匯入。綁定來源版本、備份摘要、目的帳號與當次 session/request generation；不得讓多視窗各自發起重複安裝。
- **隔離準備器**：只在擁有權明確的 staging 內準備資料，沿用原生容量、UUID／欄位合併、附件及 domain 驗證。準備結果不是 durable commit，也不是 cloud ACK。
- **提交／復原邊界**：由原生帳號交易能力執行最後重驗與安裝；App 協調器不能藉布林值、任意 URL 或替換 store 路徑自行取得寫入能力。
- **狀態投影**：分開表示等待確認、準備中、來源已變、帳號已變、需要復原、本機已安裝與待同步；不能把本機安裝成功顯示成全部設備已同步。

目前 `SyncAccountStorage.open` 明確不遷移 global storage，`SyncBootstrapSourceAccess` 只讀取原生帳號 working set。這些入口不能直接拿來接受 legacy URL。新的來源能力與持久 receipt 必須另有精確儲存契約後才能實作；本規格不發明可繞過它們的 adapter。

## 4. 確認與準備順序

1. 驗證來源可合法使用，取得完整且受容量約束的備份，記錄來源版本與檔案內容摘要。備份不包含用來改綁帳號的權限；原始同步／Watch 證據另依原有來源保留規則保存。
2. 以當次有效帳號證據準備目的帳號的隔離合併；必要網路等待期間，原本合法的本機編輯仍可進行。來源改變即讓本次準備失效，不能持續使用舊快照。此階段不傳送來源內容；真實雲端讀取仍受獨立啟用與授權門檻約束。
3. 在有效準備結果上呈現確認：說明將合併至目前 iCloud 帳號、原資料已備份、相同 UUID 沿用既定合併規則、不同 UUID 不因同名刪除，以及舊待送 Watch 指令不會改綁。不得為此儲存或顯示猜測的 Apple ID 郵件。
4. 使用者確認後，重新驗證 exact source、backup、target account、session 與準備結果；只有實際提交的必要區間才停止來源寫入並排空已開始的工作。
5. 排空後再次重驗來源與完整資料。不一致即停止安裝，回到重新準備／確認；不得在已失效 store 上重新開啟寫入。
6. 通過原生提交契約才安裝目的 working set、建立必要 journal 與持久交易證據；完成合法 handoff 後才發布新 session。ordinary engine、send、ACK 仍遵守原有門檻。

來源版本不能只用牆鐘、檔案修改時間或 UI 計數器代替；必須涵蓋結構化內容、參照附件與會影響安裝的來源證據。缺失、替換及來源路徑身分變動都須能使其失效。目的帳號 A→B→A 後，舊 A 的確認仍失效，不能只比較相同帳號 hash。

既有 `JSONProjectStore.exportBackup` 在開始和返回時都要求 write access；`revokeSessionWrites` 不可逆。因此不得先 revoke 再 export，也不得為網路準備提前永久撤銷合法本機使用。失敗後若需要恢復本機會話，必須先驗證來源安全，再建立新會話，不復活舊 generation。

## 5. 取消、重開與持久交易要求

| 發生時間 | 必須保證 |
| --- | --- |
| 確認前或隔離準備中取消 | 無目的 live 安裝、無上傳；保留原始內容及需保留的備份／證據 |
| 確認後但提交前來源或帳號變動 | 舊確認失效，無新帳號寫入；新嘗試需重新準備及確認 |
| 提交已開始時取消或帳號失效 | 撤銷後續發布／傳輸，等待原生交易的真實結果並依帳號復原契約處理；不保證已提交部分可當作未發生 |
| 中斷後沒有有效 commit 證據 | 依真實交易狀態恢復或回復；不憑 UI 狀態、空目錄或單一 marker 宣稱成功 |
| 已 commit 但 App 尚未發布就中斷 | 先驗證同帳號交易、canonical/journal/附件及必要保留證據，再重開；不重新匯入同一交易 |
| receipt、來源或復原資料損毀／不完整 | 阻擋相關接入，保留資料；不偽造 receipt、不降級成新匯入 |

未提交嘗試在程序重啟後不自動沿用記憶體確認。恢復已提交交易則不是發起新的使用者匯入；必須由原生持久證據判定，不能僅靠確認紀錄重播。

持久交易設計至少需綁定格式版本、唯一交易 identity、exact 目的帳號、來源內容／備份摘要、原生安裝結果及恢復所需證據；不得宣稱紀錄本身證明來源歷史。寫入順序、原子性、損毀拒絕、容量與舊版重開相容是下個儲存設計切片的必要輸入，不由本文件暗定新的磁碟格式。未完成該切片前，本契約只能做隔離建模與測試，不可接上真實安裝。

保留原本容量及清理界線；空間不足即不安裝，不刪舊附件、pending 或復原資料以騰出空間。沒有新增自動刪除期限；既有需認證的清理不能由 App 取消動作取代。

## 6. Watch 與合併不變量

使用者確認內容匯入不授予把舊 prepared command、pending queue、ACK 或處理 ledger 改綁到新帳號的能力。也不能直接丟棄這些資料再聲稱 counter／reminder exactly-once 已保持。

如果來源計數器狀態與待處理 Watch 證據無法安全分離，該匯入停在待處理狀態，保留來源；必須先完成對應保留／轉換契約與測試，不能發布部分合併。Watch 新 wire、混合版本及實機重新握手仍是獨立門檻，本規格不設計或批准它們。

保留現有 UUID、欄位合併、附件衝突兩份保留、刪除證據、counter revision 與提醒規則；使用者內容不翻譯。不同 UUID 同名不刪除，相同 UUID 不另造新 identity 來逃避衝突驗證。

## 7. 驗收條件

先以隔離資料和可控制帳號／transport 執行；不接觸真實帳號或使用者 store。下列為要求，並非已通過結果：

1. 合法本機但無歷史歸屬證據，沒有確認時目的 store/journal/send 均不變；本機仍可編輯。
2. 錯帳號、未知帳號、受保護 recovery、損毀來源不能由確認入口解鎖或重新分類。
3. 備份失敗、缺附件、hash 不符、來源替換或容量不足，不安裝且原資料保持；驗證備份確實對應被確認來源。
4. 準備前後及最終排空前後的新編輯使舊確認失效；資料不倒退，不能只斷言 Task 已取消。
5. A→B、A→B→A、舊查詢晚到、重複點擊及多視窗不沿用舊確認，不重複安裝。
6. 對準備、提交與發布的每個持久前綴注入錯誤及真實程序終止；同一路徑重開、不重播 fixture，觀察原資料、備份、journal、receipt 和 canonical 結果。
7. commit 後發布前終止可識別已提交交易；重開不重複產生 domain import 或 journal mutation。
8. 遺失／損毀／錯帳號／不完整持久證據拒絕使用，原證據仍保留；舊版重開不提前清除復原所需內容。
9. 有 Watch pending/prepared、counter/reminder 與刪除證據的完整來源，不改綁、不靜默清除、不跳過 whole-graph 驗證。
10. 相同 UUID、同名不同 UUID、附件並行版本及完整關聯符合既有規則；原始內容與可還原備份可核對。
11. 正常 shipping/screenshot startup 的新 import/live factory 呼叫數為零；本機成功不冒稱雲端已同步。
